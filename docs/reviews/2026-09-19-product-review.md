# UI 升级与产品体验复审

审查基线：`3344e78`，工作区开始时干净。重点检查 `ff06935..3344e78` 的统一 UI、帮助面板、三批素材与移动布局调整，并回看水排序、叠叠消的近期改动。此次交付为审查和改进方案，不修改游戏实现，不推送、不部署。

结论：基础构建与规则测试通过，但当前版本不能据此认定完成产品级验收。共享新手说明、五子棋缩放和生产验收入口存在可复现缺陷。以下优先级中，P1 应在下一次发布前处理，P2 应在后续体验批次处理。

## 确认的问题

### 1. P1：所有共用帮助面板的步骤正文被背景覆盖

- 位置：`src/ui/phaser/help.ts:118-149`。
- 复现：清空测试浏览器存储，进入接水管，等待首次说明；iPad 竖屏能看到标题和目标，但三条操作步骤几乎完全不可见。
- 原因：步骤与编号先加入 Container，随后才加入 alpha=0.98 的卡片背景，背景覆盖文字。另有独立布局错误：步骤末行中心约为逻辑 y=615.5，关闭按钮中心约为 y=612.1；仅调绘制顺序仍会重叠。
- 改进：固定为遮罩→卡片→内容→按钮的层级；用同一套实际排版结果计算卡片高度与按钮位置，正文超高时提供滚动或分页，不能只截断 panelH。
- 回归要求：首次进入与手动打开均检查每条正文可见、正文与按钮不相交；覆盖手机及 iPad 横竖屏。
- [当前浏览器证据](evidence-2026-09-19/help-pipes.png)。

### 2. P1：五子棋放大后返回、声音、模式等顶栏消失

- 位置：`src/games/gomoku/scene.ts:85-92, 222-242`。
- 复现：768×1024 打开五子棋，点击 DOM 的“＋”，到 1.5 倍时顶栏已移出视口，只剩棋盘和 DOM 缩放按钮。
- 原因：直接缩放整个 main camera；`setScrollFactor(0)` 仅取消滚动影响，不取消相机缩放。
- 改进：棋盘单独使用 camera/container，顶栏与帮助层使用独立不缩放的 UI camera；限定棋盘视口。以真实屏幕坐标验证返回、重开、声音、模式在各档缩放后仍可点击。
- 同处代码风险：panWhenZoomed 每次移动都会重写 dragStart，而抬手又用它判断是否拖动，应该拆成按下起点、上一帧位置和 didDrag。此次鼠标拖动未复现误落子，暂不把它计为确认缺陷。
- [当前浏览器证据](evidence-2026-09-19/gomoku-zoom.png)。

### 3. P1：生产包验收脚本必定在离线验证前失败

- 位置：`scripts/browser-smoke.mjs:89-91`。
- 复现：生产构建后启动 preview，执行 `PRODUCTION_ONLY=1 APP_URL=http://127.0.0.1:4187 pnpm test:browser`。
- 实测错误：`Failed to fetch dynamically imported module: .../src/ui/help-content.ts`。
- 原因：进入 PRODUCTION_ONLY 分支之前，无条件从开发源码 URL 导入帮助清单；生产包没有这个模块路径。
- 改进：生产验收必须只操作真实产品入口，不读取 `/src/`；把新用户说明作为可操作流程纳入测试。旧用户测试数据可以从 Node 侧明确注入，但不能依赖生产环境不存在的源码。
- 回归要求：preview 上真实完成 SW 接管、离线重载和游戏操作；新增“发现 /src/ 请求即失败”的检查。

### 4. P2：俄罗斯方块手动看规则时仍继续下落

- 位置：`src/games/tetris/scene.ts:90-93,296`。
- 首次帮助通过 hooks 暂停，顶栏“规则”直接调用 showHelpPanel，没有相同暂停逻辑。浏览器调用同一手动帮助入口后，实际 `paused === false`。
- 改进：提供统一 openHelp 方法，记录打开前的暂停状态，暂停逻辑时钟与锁定计时；关闭后恢复原状态。不要对原本已暂停的局面无条件恢复。
- 回归要求：从运行态和暂停态分别打开帮助，等待超过一次下落周期，验证棋盘不变；关闭后状态准确恢复。

### 5. P2：帮助面板关闭后仍保留 resize 与生命周期监听

- 位置：`src/ui/phaser/help.ts:154-173`。
- close 只销毁画面，事件清理直到场景销毁才执行；每次打开都会新增 resize/SHUTDOWN/DESTROY 监听。
- 浏览器实测：连续调用打开/关闭 10 次，resize 监听器数量从 4 增加到 14。
- 改进：共用幂等 dispose，在正常关闭、SHUTDOWN、DESTROY 三条路径移除全部监听，并取消相关 tween。dense 分支创建后没有纳入 layer 的 icon 也应销毁。
- 回归要求：连续打开关闭 20 次后监听器与显示对象数量回到基线，场景离开后无新增残留。

### 6. P1：帮助面板不能阻止背后棋盘操作

- 位置：`src/ui/phaser/help.ts:54-58`。
- 复现：768×1024 新用户进入接水管，保持帮助打开，点击画布逻辑坐标 `(630,650)`。实测状态由 `{moves:0,help:true}` 变成 `{moves:1,help:true}`，帮助尚未关闭而背后管子已旋转。
- 原因：Rectangle 的命中区域使用了负半宽/半高起点，与输入系统处理显示原点后的局部坐标不匹配；面板本体也没有提供完整拦截。另外，场景级 pointer/keyboard 处理不能仅靠上层对象遮挡来禁用。
- 改进：改用正确的形状默认命中区域，建立统一 modal 输入门禁，同时拦截关闭手势的完整 down/up 生命周期，防止关闭时穿透。逐个检查用场景级 pointer 处理的游戏。
- 回归要求：遮罩四角、正文区域、关闭按钮均需实际点击；面板显示期间棋盘状态保持不变，键盘也不能改变棋局，关闭当次手势不触发走子。

## 验收与资源方面的缺口

1. `pnpm check` 实测通过：38 个测试文件、225 个测试，TypeScript 和生产构建通过。AGENTS.md 仍写 213 个测试，已经过时。
   `APP_URL=http://127.0.0.1:5187 pnpm test:browser` 也完整通过，包括 iPad 两种方向、续玩/输入/音频状态以及连续切换检查。这个结果仅证明现有脚本覆盖的路径；上述新用户问题是在独立干净浏览器中补测发现的。`git diff --check` 通过。
2. 主浏览器脚本主动标记全部帮助“已看过”。注释称由 help-verify 类脚本验收，但当前仓库 tests/scripts 没有对应的可执行文件，形成了覆盖空档。应分别保留新用户、旧用户、已有存档三种场景，不能以关闭新功能来证明新功能正常。
3. 生产 Workbox 输出为 101 条、36990.70 KiB 预缓存，约 36.1 MiB。单张卡桌背景约 2.26 MB，通过提高单文件缓存上限使构建通过，并没有降低资源成本。需要按实际显示尺寸优化图片，剔除未引用/重复资源，并设单图与总预缓存预算。不能直接删掉离线资源来让数字变小。慢网安装耗时和 Safari 存储行为本次未实测。
4. 仓库约束冲突：AGENTS.md §12 要求默认提交→推送→部署，§13 要求明确部署授权，§14 又要求没有 push。应合并为唯一发布规则；在消除冲突前，本次审查不进行外部发布操作。
5. 当前结果不等于 24 款全部难度、全部结算状态均完成验收。Safari 真机、人耳听感、主屏幕更新没有在本次验证，不能标记通过。生产离线验证被上面的脚本错误阻断，也不能沿用旧报告冒充当前结果。

## 约束 Zcode 的可执行方案

仅增加长篇提示词不足以防止这些问题。建议把约束分成任务范围、自动门禁、独立验收和权限四层。以下为待采用方案，不声称已配置 Zcode 或远端分支保护。

### 任务范围

- 每批一个可验收目标，先做一款游戏作为样板，通过后再推广共享组件；避免“全站产品级升级”这种无边界任务。
- 开工前填写允许修改的路径、必须保留的行为、明确不改的规则/存档/依赖，以及验收动作；超范围修改必须在交付中单独列出。
- UI 重构与玩法规则修改分批提交。规则缺陷先提交能失败的复现测试，再实现修复。
- 未经任务明确要求，不修改测试门槛、删除断言、扩大资源限制或把失败项目改为跳过。

### 自动门禁

建议新增独立 CI 作业：check → 新/老用户浏览器验收 → 生产 preview 离线验收 → 资源预算。失败必须阻止合并。验收脚本修改需要额外审查，不能让实现者通过削弱脚本自行取得“通过”。

| 修改类型 | 必须提供的证据 |
| --- | --- |
| 布局/共享 UI | 手机、iPad 横竖屏；首屏、帮助、操作后、弹窗/结算；点击区域与文字可见性 |
| 输入/缩放 | 真正触控事件、拖动与点击区分、缩放后顶栏可用、旋转不中断棋局 |
| 计时/动作游戏 | 弹窗暂停与恢复、切后台、连续操作、回合结束 |
| 存档 | 老存档加载、坏档、快速操作不被迟到读取覆盖 |
| 素材/PWA | 缓存体积、缺失请求、生产包离线、更新不打断游戏 |

每份证据必须绑定代码提交号、运行命令、退出码、视口和输出文件。截图必须有人实际打开检查；“截图文件已生成”不是视觉验收。未测、失败、通过三种状态必须分别记录。

### 独立验收与权限

- Zcode 在任务分支提交，由另一轮审查根据 diff 和原始日志验收；不能仅凭其自己写的完成总结合并。
- 通过仓库托管平台的保护规则禁止直接写 main，并要求外部 CI 检查。具体配置需在单独授权的维护任务中执行。
- 开发执行环境不提供部署 SSH 私钥或远端写权限；发布由单独受控流程执行。本地 hook 只能减少失误，可被跳过，不是可靠权限边界。
- 统一 AGENTS.md 的发布规则后，只保留一个授权来源，避免 agent 选择其中最宽松的条款。

### 可直接交给 Zcode 的任务模板

```text
目标：修复 [具体问题]。本批只处理这一个目标。
基线提交：[SHA]。
允许修改：[路径]。
保留行为：[规则、触控、存档、生命周期等不变量]。
先证明问题：提供稳定复现步骤；规则问题先写失败测试。
修复后运行：pnpm check、git diff --check，以及 [指定浏览器用例]。
不得删除/跳过既有断言，不得预置状态绕过本次变更的用户流程。
涉及共享 UI，必须在新用户/旧用户状态和三种视口真实操作验收。
交付：提交号、改动文件、每条验收的命令/退出码/证据、未验证项。
本任务只本地提交，不推送、不部署，不修改服务器。
```

建议实施顺序：先修复生产验收入口并补帮助回归 → 修共享帮助面板 → 修五子棋缩放与方块暂停 → 建立发布门禁与资源预算 → 再继续美术推广。
